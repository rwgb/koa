### Top 3 Highest-Risk Items

1. **SEC-001 — analyze_image reads arbitrary filesystem paths** — The tool explicitly opts out of the sandbox and its own description advertises this. A single jailbreak turn can exfiltrate `~/.koa/credentials` (containing `ANTHROPIC_API_KEY`, `KOA_WEB_TOKEN`, OAuth refresh tokens) as base64 in the model response. No config flag, no audit log, no mitigation today.
2. **GAP-04 — AgentLoop `_turnImpl` tool-timeout and MAX_TOOL_ITERATIONS entirely untested** — A tool that never returns hangs the server indefinitely; a bug in the iteration guard causes an infinite loop in production. This is the hot path of the entire product and it has no test coverage.
3. **GAP-01 — OAuth CSRF nonce flow has 0% test coverage** — The Gmail and Google Calendar callback handlers validate a one-time nonce, but every branch (missing nonce, replayed nonce, exchange failure) is untested. A regression here allows OAuth token hijacking via CSRF with no warning.

## P0 — Fix Immediately

### [SECURITY] SEC-001 — analyze_image reads arbitrary filesystem paths with no sandbox

- **File:** `src/agent/tools/files.ts` (line 140)
- **What:** The tool explicitly bypasses `sandboxPath()` and advertises in its description that it accepts "absolute paths anywhere on the filesystem," allowing a jailbroken agent turn to base64-exfiltrate `~/.koa/credentials` or any other file the process user can read.
- **Fix:** Pass the resolved path through `sandboxPath()` against a configurable `imageRoot` allowlist; remove the "not restricted to project root" language from the tool description; add an audit log entry on every invocation.
- **Effort:** S

### [SECURITY] SEC-002 — Slack `url_verification` challenge reflected before signature check

- **File:** `src/server/routes/webhooks.ts` (lines 48–50)
- **What:** Any caller can POST `{"type":"url_verification","challenge":"<anything>"}` and receive the challenge echoed back, permanently, with no signature validation — the bypass exists long after initial app setup.
- **Fix:** Run the Slack signing-secret HMAC check before reading `challenge`; additionally, validate that `challenge` matches `/^[a-z0-9]{1,64}$/` before echoing.
- **Effort:** S

### [SECURITY] SEC-003 — Slack `response_url` POSTed without SSRF validation

- **File:** `src/channels/slack.ts` (line 88)
- **What:** `replyToSlack()` calls `fetch(opts.responseUrl)` where `responseUrl` comes from the untrusted Slack payload; `validateSafeUrl()` is called for all other outbound HTTP in this file but not here, allowing a crafted payload to pivot to internal services.

- **Effort:** S

### [SECURITY] SEC-004 — Telegram accepts messages from any chat ID — no inbound allowlist

- **File:** `src/channels/telegram.ts` (line 69)
- **What:** `handleMessage()` passes all inbound Telegram messages directly to `loop.turn()` with no chat-ID check; any user who knows the bot token can control the AI agent, read project memory, and trigger bash commands.

- **Fix:** Add `cwd: projectRoot` to the `execa` call; add a blocked-pattern denylist for obvious reverse-shell patterns; emit an audit log entry on every bash execution; document that `sandboxBackend=docker` is required when untrusted channels are enabled.
